## 1. Goals, scope, summary of decisions

### 1.1 Goals

1. The whole console in five languages: German (source), English, French, Italian and Dutch. Every text the
   web shows, every e-mail and the invoice PDF.
2. Each person picks a language once (profile, with flag tiles); it applies after login on every device and to
   the e-mails sent to that person. Before login the choice on the login page applies.
3. Customers get invoices, reminders and payment confirmations in the language of their billing profile.
4. Staff can see and edit every text in every language without a deploy (Verwaltung > Übersetzungen), find what
   is missing or outdated, and translate the rest with Claude (Mass Translate) at a known cost.
5. Every translation, from the repository, typed in the admin or written by Claude, passes the same automatic
   checks (19.4), so no German leftovers, informal address, broken placeholders or French spacing errors go live.
6. Legal texts (`LEGAL_KEYS`, today the AI data notice) are never machine-translated and never shown in an
   outdated translation.

### 1.2 Scope

In scope: dictionaries in `packages/shared`, the web runtime with lazy locale chunks and database overrides,
language pickers, number, date and money formats per locale, the error text mapping in the web, e-mail templates
and the invoice PDF from dictionary keys, the billing language, the translation admin page with filters, inline
editing, glossary, style notes, import and export, Mass Translate as a background job, stale detection with stamp
files, the shared checks, the migration `0011_i18n`, permissions, audit, tests and docs.

Stays English on purpose (decision 7 of the plan): API error and validation messages (the public API contract),
logs, audit action names and audit details, the API Explorer, provider error texts passed through. The web
translates the generic error codes and every AI and i18n code (7); every other specific API message stays
English in every UI language.

Stays as entered: stored data such as invoice lines, credit ledger descriptions ("Rechnung WL-2026-00001"),
organization and product names (products can carry translations, plan O14), notes, and the QR bill message
"Rechnung <Nr>" (8.3).

Out of scope (O31): the TypeScript file-set export (16.3). Plural rules stay as today: call sites pick a key by
count (`*One`, `year1`/`yearsN`); ICU messages are not introduced.

## 2. Locales

### 2.1 The five locales and LOCALE_META

`packages/shared/src/i18n/locales.ts` (O1, re-exported from `packages/shared/src/index.ts`, imported by `ai.ts`
as `./i18n/locales`):

```ts
export const LOCALES = ['de', 'en', 'fr', 'it', 'nl'] as const;
export type Locale = (typeof LOCALES)[number];

/** Every locale except the source. Translations, stamps, product translations and Mass Translate use these. */
export const TARGET_LOCALES = ['en', 'fr', 'it', 'nl'] as const;
export type TargetLocale = (typeof TARGET_LOCALES)[number];

export const SOURCE_LOCALE = 'de' satisfies Locale;

export interface LocaleMeta {
  /** Name of the language in itself, shown next to the flag in every UI language. */
  native: string;
  /** English name, for logs, scripts and prompts. */
  english: string;
  /** ISO 3166-1 alpha-2 code of the flag (6.4). */
  flag: 'DE' | 'GB' | 'FR' | 'IT' | 'NL';
  /** BCP 47 tag for every Intl call (2.3). */
  intl: 'de-CH' | 'en-GB' | 'fr-CH' | 'it-CH' | 'nl-NL';
}

export const LOCALE_META: Record<Locale, LocaleMeta> = {
  de: { native: 'Deutsch', english: 'German', flag: 'DE', intl: 'de-CH' },
  en: { native: 'English', english: 'English', flag: 'GB', intl: 'en-GB' },
  fr: { native: 'Français', english: 'French', flag: 'FR', intl: 'fr-CH' },
  it: { native: 'Italiano', english: 'Italian', flag: 'IT', intl: 'it-CH' },
  nl: { native: 'Nederlands', english: 'Dutch', flag: 'NL', intl: 'nl-NL' },
};
```

The native names are not dictionary keys: a language is always offered in its own name, whatever the UI
language. Where a second line helps (profile tiles, 6.1), the name of the language in the current UI language
comes from `Intl.DisplayNames([intl], { type: 'language' })`, so no keys are needed for it either.
`{language}` placeholders (for example `billing.product.translations.name`, plan 5.3) receive `LOCALE_META[l].native`.

### 2.2 Shared types and helpers

Also in `locales.ts`:

```ts
export function isLocale(value: unknown): value is Locale;
export function isTargetLocale(value: unknown): value is TargetLocale;

/**
 * 'fr', 'FR', 'fr-CH', 'fr_CH' -> 'fr'; 'gsw' (Swiss German) -> 'de'; anything else -> null.
 * Used for stored values (users.locale, billing_profiles.locale), query strings and headers.
 */
export function normalizeLocale(value: unknown): Locale | null;

/**
 * First supported language of a list such as navigator.languages, in order. Each entry goes through
 * normalizeLocale. Without a match: fallback (default 'en', as today: a browser in Spanish gets English,
 * which more people read than German).
 */
export function matchLocale(candidates: readonly string[], fallback?: Locale): Locale;

/** Lookup order for a key: fr -> ['fr', 'en', 'de'], en -> ['en', 'de'], de -> ['de']. */
export function fallbackChain(locale: Locale): readonly Locale[];

/** LOCALE_META[locale].intl */
export function intlLocale(locale: Locale): string;
```

The fallback chain is fr/it/nl -> en -> de (D1): English is complete by type (3.1), and a French, Italian or Dutch
reader understands English better than German. `de` is reached only for keys that exist in no other bundle,
which the key parity check (19.4 check 1) rules out for en, and for legal keys (8.1).

`interpolate.ts`:

```ts
export type I18nParams = Record<string, string | number | null | undefined>;
/** Replaces {name} with String(params.name ?? ''). Unknown placeholders stay as they are. */
export function interpolate(text: string, params?: I18nParams): string;
```

`placeholders.ts`:

```ts
/** {name}: a letter, then letters, digits or underscores. JSON examples such as { "a": 1 } are not placeholders. */
export const PLACEHOLDER_RE: RegExp; // /\{([A-Za-z][A-Za-z0-9_]*)\}/g
/** Placeholder names in order of appearance, duplicates kept. */
export function placeholdersOf(text: string): string[];
/** Multiset difference: what the value lacks and what it adds compared to the German text. */
export function comparePlaceholders(source: string, value: string): { missing: string[]; extra: string[] };
export function lineBreakCount(text: string): number;
```

`types.ts` (exported with `export type * from './i18n/types'` from the package index, F4):


Type-only imports never pull a dictionary into a bundle. The package index exports no dictionary value (F4);
dictionaries are reached only through the subpath exports `@weblion/shared/i18n/<name>`.

### 2.3 Formatting per locale

One rule for every formatter: the Intl tag is `LOCALE_META[locale].intl`; no `locale === 'de' ? ... : ...`
ternary survives.

| What | Web | API |
|---|---|---|
| Dates, times, relative times | `lib/format.ts`: `formatDate`, `formatRelative` with `intlLocale(locale)` | `mail/templates.ts` `mailDate(date, locale)` (long date, `Europe/Zurich`) |
| Numbers | `formatNumber(value, locale)` | |
| Durations | `formatDuration`: day unit per locale `{ de: 'T', en: 'd', fr: 'j', it: 'g', nl: 'd' }`, hours and minutes stay `h`, `m` | |
| Money | shared `formatMoney(amount, currency, locale: Locale = 'de')` with `intlLocale(locale)` | billing mails and the PDF call it with `'de'` (Swiss format, D2) |
| Percent | `formatPercent` keeps `"12.5 %"`; `pages/billing/money.ts` `formatRate(bp, locale)` with `intlLocale` | PDF: de-CH |
| Country names | `Intl.DisplayNames([intlLocale(locale)], { type: 'region' })` | PDF address block in the invoice language |
| Units on invoice lines | `unitForInterval(interval, t)` with keys `billing.unit.*` (18.1) | |

Changes against today:

- English switches to en-GB everywhere. Today English numbers use en-GB but English money uses en-CH
  (`packages/shared/src/billing.ts:298-304`), so `CHF 1’234.50` in English becomes `CHF 1,234.50`.
- French and Italian use the Swiss variants (fr-CH: `1 234,50 CHF` with a narrow no-break space, it-CH:
  `CHF 1’234.50`), Dutch uses nl-NL (`CHF 1.234,50`): a Dutch customer of a Swiss business reads Dutch formats.
- Invoices keep Swiss formats in every language (D2): `apps/api/src/modules/billing/pdf.ts:39-40` stays de-CH,
  dates stay `formatDateCH` (dd.mm.yyyy). Billing mails (invoice, reminder, payment, credit) also keep
  `formatMoney(..., 'de')` and `formatDateCH`, so the amount in the mail reads exactly as on the attached PDF and
  in the bank statement. Only their texts are translated. The invitation mail formats its date in the mail
  language (`mailDate`).

Files with locale ternaries or fixed Intl tags today, all changed by U2: `apps/web/src/lib/format.ts:3`
(`intlLocale`, and `formatDuration`), `components/metric-chart.tsx`, `pages/billing/money.ts:10` (`intl`) and
`:108-116` (`unitForInterval`), `pages/mail/units.ts` (`formatMailSize` and its callers `pages/admin/mail.tsx`,
`pages/mail/bits.tsx`, `pages/mail/mailboxes.tsx`, `pages/mail/overview.tsx`), `pages/media/bits.tsx`,
`pages/monitoring/bits.tsx`, `components/layout/app-shell.tsx:234-235` and `pages/auth/login.tsx:42-44` (the
de/en toggles, replaced by the pickers of 6), `components/server-bits.tsx:52-120` (German `aria-label` literals
of `Flag`, replaced by Intl region names), aria literals in `pages/org/policies.tsx`,
`pages/servers/tabs/settings.tsx`, `pages/servers/list.tsx`; on the API side `mail/templates.ts:56-63`
(`mailLocale`, `mailDate`) and `modules/billing/pdf.ts:42` (`regionNames` in German only).

Money input (`pages/billing/money.ts:13-27`): `normalizeDecimal` removes `'`, `’` and spaces and turns the first
comma into a dot, then `parseMoney` accepts at most two decimals. A Dutch or French user typing `19,90` gets
1990; `1.250` and `12.500` (Dutch thousands separators) have three decimals and give `null`, so they cannot be
misread as 1.25 or 12.5 (review finding 18, rejected with tests, 20.3). The form shows its usual "invalid amount"
error for them. `1.250,50` gives `null` too (two separators). No parser change.

### 3.1 Location, typing, aggregators, catalog

All dictionaries move from `apps/web/src/i18n/` to `packages/shared/src/i18n/` (O2, F1), so the API can list
keys and source texts and render e-mails and PDFs with the same texts and overrides as the web (plan decision 28).
`apps/web/src/i18n/` is deleted.

```
packages/shared/src/i18n/
```

Typing per section file (example `core`):

```ts

// sections/core.en.ts (complete: a missing key fails the typecheck)

// sections/core.fr.ts (partial: a new German key never breaks the build)

```

Files for fr, it, nl are written by the translation units (plan 7): keys in German order, no comments, single
quotes, `\n` kept, formatted by prettier. de and en keep their comments.

Web aggregators (`de.ts` ... `nl.ts`) spread the 14 web sections in `WEB_SECTIONS` order and export a chunk marker
for the build check (5.4):

```ts
// de.ts
export const I18N_CHUNK = 'wl-i18n-chunk:de';
export const de = { ...coreDe, ...adminDe, ...aiDe, ...translationsDe, ...hostingDe, /* ... */ ...uptimeDe } as const;
// en.ts

// fr.ts (it.ts, nl.ts alike)
export const I18N_CHUNK = 'wl-i18n-chunk:fr';
export const fr: Partial<Record<TranslationKey, string>> = { ...coreFr, /* ... */ };
```

`email` and `pdf` are not in any web aggregator (O33, review finding 19): their texts would go to every browser
for nothing, in every locale chunk. `server.ts` adds them for the API:

```ts
export const serverDe = { ...de, ...emailDe, ...pdfDe } as const;
export const serverEn: Record<ServerTranslationKey, string> = { ...en, ...emailEn, ...pdfEn };
export const serverFr: Partial<Record<ServerTranslationKey, string>> = { ...fr, ...emailFr, ...pdfFr };
// serverIt, serverNl alike
/** Every section in every locale, for the catalog, the stamp script and the report. */
export const SECTION_SOURCES: Record<SectionName, Record<Locale, Readonly<Record<string, string>>>>;
```

The web never imports `server.ts`, `catalog.ts` or a section file directly; only `lib/i18n-loader.ts` (and tests)
import the aggregators. A test enforces it (20.3, `lib/i18n-imports.test.ts`).

Key types (2.2): `TranslationKey` for the web (`t()` in React), `ServerTranslationKey` for the API (mail
translator `Tr`, PDF, `ctx.i18n.t`). An `email.*` key used in the web, or a web-only key that the API needs, is a
type error.

`catalog.ts` builds the immutable view the API works with (F2; `I18nService`, filters, the stamp script, the
report and `i18n:apply` use it):

```ts
export type Stamp = readonly [sourceHash: string, valueHash: string];

export interface I18nCatalog {
  /** Every key in German order: section by section in SECTIONS order, inside a section in file order. */
  keys: readonly ServerTranslationKey[];
  sections: readonly SectionName[];
  sectionOf(key: string): SectionName | undefined;
  has(key: string): key is ServerTranslationKey;
  /** Compiled values per locale (de and en complete, the others partial). */
  bundles: Record<Locale, Readonly<Partial<Record<ServerTranslationKey, string>>>>;
  /** Stamps per target locale (4). */
  stamps: Record<TargetLocale, Readonly<Partial<Record<ServerTranslationKey, Stamp>>>>;
  /** Keys that only the API uses (sections email and pdf); never sent to the web (13). */
  serverOnly: ReadonlySet<string>;
}

/** Builds a catalog; the default arguments are the repository sections and the 64 stamp files. */
export function buildCatalog(sources?: typeof SECTION_SOURCES, stamps?: StampFiles): I18nCatalog;
/** buildCatalog() once, memoized. */
export function loadCatalog(): I18nCatalog;
```

The stamp files are imported statically as JSON (`resolveJsonModule` is on in `tsconfig.base.json`), 64 fixed
import lines: the set of locales and sections never changes at runtime, every file exists from F on (fr, it, nl
start as `{}`), and tsup bundles them into the API (`apps/api/tsup.config.ts` already bundles `@weblion/shared`).
Tests pass their own catalog through `BuildOptions.i18nCatalog` (F17) built with `buildCatalog()` from small
sources (`apps/api/test/i18n-fixtures.ts`, `testCatalog()`).

### 3.3 Module and permission labels as keys

Today the labels are `{ de, en }` objects: `PermissionDef.label` (`packages/shared/src/permissions.ts:30-44`,
built by `def(group, de, en, extra)`) and `ModuleDef.label`/`description` (`modules.ts:23-29`). They cannot take
a third language without changing every definition. They become keys (O3, F5):

- `module.<m>.label`, `module.<m>.description` for the 8 modules (16 keys in `core`, texts = today's `MODULE_DEFS`).
- `perm.<action>` for all 93 actions of today plus the 5 new ones (98 keys in `core`, texts = today's labels;
  `perm.ai:use`, `perm.ai:settings`, `perm.platform:ai:use` with the texts of ai 3.2, `perm.platform:i18n:read`
  and `perm.platform:i18n:write` with the texts of 11). The key contains the action verbatim, colons included
  (`perm.server:backup:create`).
- `perm.group.<g>` stays (14 in `core`, 4 in their sections), plus `perm.group.ai` in `core`.

Shared code after the change: `def(group, extra)` without labels, `PermissionDef` without `label`, `ModuleDef`
keeps only `actions`. The typecheck proves every label exists: `t(\`perm.${p}\`)` with `p: Permission` has the
type of a union of 98 literal keys, each of which must be a `TranslationKey`.

`GET /meta` (`apps/api/src/modules/meta/routes.ts:19-35`) keeps its response shape for API clients: `permissions`
is built as `{ ...PERMISSIONS[p], label: { de: ctx.i18n.t('de', \`perm.${p}\`), en: ctx.i18n.t('en', \`perm.${p}\`) } }`
for every action, so the labels include overrides. No other locale is added to `/meta` (it is a stable API).

## 4. Stale detection

### 4.1 Purpose

"Veraltet" means: the German text changed after this translation was written, so the translation may say
something else. The admin needs it for every cell (filter "Veraltet", 15), the integrator needs it to find the
keys that units changed after F (plan 8.2, `i18n:report --stale`), and legal keys must never be served stale (8.1).

For overrides the database row carries the hash of the German text it was written against (`source_hash`, 10).
For compiled translations in the repository there is no row, and comparing the text with German says nothing
(221 values are the same in German and English today). So the repository records, per locale and section, which
German text each compiled translation was written against: the stamp files.

The hash is `sourceHash(text)` in `apps/api/src/i18n/hash.ts`: SHA-256 of the NFC-normalized text, hex, first 16
characters. The same function hashes values (`valueHash`). The comparison is always against the effective German
text: the German override if there is one, else the compiled German (8.1). So a German override makes every
translation of that key stale, which is right: the source changed.

### 4.2 Stamp files and allowlists

`packages/shared/src/i18n/stamps/<locale>/<section>.json` for `en`, `fr`, `it`, `nl` (O13): one object, keys in
German order, value a pair `[sourceHash, valueHash]`:

```json
{
  "common.actions": ["5d41402abc4b2a76", "1f3870be274f6c49"],
  "common.add": ["0cc175b9c0f1b6a8", "92eb5ffee6ae2fec"]
}
```

- `sourceHash`: hash of the German text the translation was written against.
- `valueHash`: hash of the translation when it was stamped. It lets the script tell an edited translation (value
  hash differs: the translator touched it, so it is current) from an untouched one (value hash equal: it stays
  stale until someone confirms it).
- A key without a translation has no stamp. A translation without a stamp counts as stale (and fails the stamps
  test, 20.2).

One file per locale and section, so the three translation units of a language never write the same file
(plan 7.1, 11).

`packages/shared/src/i18n/allowlists/<locale>/<group>.ts` for `fr`, `it`, `nl` and groups `a`, `b`, `c` (O13):
false positives of the heuristic checks (19.4 checks 3 to 6 and 11), one array per check, each entry with an
English reason comment:

```ts
import type { Allowlist } from '../../checks';

export const allowlist: Allowlist = {
  germanOk: [
    // "Webhosting" is the usual term in Swiss French as well.
    'perm.group.webhosting',
  ],
  informalOk: [],
  lengthOk: [],
  glossaryOk: [],
  typographyOk: [],
};
```

`checks.ts` merges the three groups of a locale (`allowlistFor(locale)`). An allowlist entry for a key that no
longer exists fails the shared test (stale allowlists hide nothing). English has no allowlists: en is checked
only by the hard checks (19.4).

### 4.3 The i18n:stamp script and the REQUIRE switches

`apps/api/scripts/i18n-stamp.ts` (F16), run as `pnpm --filter @weblion/api i18n:stamp`:

```
i18n:stamp [--locale <en|fr|it|nl>] [--section <name>] [--key <key>] [--confirm] [--check]
```

For each selected locale (default: all four) and section (default: all 16), with `de` = the compiled German text
(stamps describe the repository, never the database):

1. For each key with a translation `v` in `sections/<s>.<locale>.ts`:
   - no stamp: write `[hash(de), hash(v)]` (new translation).
   - stamp with `valueHash !== hash(v)`: write `[hash(de), hash(v)]` (the translator changed it against the
     current German).
   - stamp with equal value hash and `sourceHash !== hash(de)`: stale. Keep it and list it, unless `--confirm` is
     given (then write `[hash(de), hash(v)]`: the translator confirms the existing text is still right).
     `--confirm` without `--section` or `--key` asks for confirmation on the terminal unless `--yes` is given.
2. Remove stamps of keys that have no translation or no longer exist.
3. Write the file in German key order, two-space indent, trailing newline; write nothing when it is unchanged.
4. Print per locale and section: new, updated, confirmed, stale (listed by key), removed.

`--check` writes nothing and exits 1 when a file would change (for CI or a pre-commit run). Exit code otherwise 0.

The units and translators run it after every change (plan 0, 7.4). `i18n:report` (U1, plan 8.2) uses the same
comparison and prints, per locale and section, missing and stale counts, with `--missing` and `--stale` listing
the keys.

Switches for the tests (plan 7.4, 8.3):

- `I18N_REQUIRE_COMPLETE` (shared test `packages/shared/src/i18n/i18n.test.ts`, check 9): `1` or `true` = fr, it
  and nl must have every key; a comma list (`fr` or `fr,it`) = those locales only. Unset: missing keys are
  allowed (they fall back to English). CI does not set it; the integrator does (plan 8.3).
- `I18N_REQUIRE_LEGAL` (API test `apps/api/test/i18n-stamps.test.ts`): same values; every key of `LEGAL_KEYS`
  must have a compiled translation in the selected locales and its stamp must be current. CI sets `1` (plan 8.3).

Always checked by `i18n-stamps.test.ts`, without switches: every stamp file parses and names only existing keys;
every compiled translation has a stamp whose value hash matches (so nobody forgets `i18n:stamp`); every en stamp
is current (English is written together with German, plan 0). The shared test reads the switches through a local
`declare const process: { env: Record<string, string | undefined> }`, because `packages/shared` has no Node types.

## 5. Web runtime

### 5.1 Lazy locale chunks: lib/i18n-loader.ts

`apps/web/src/lib/i18n-loader.ts` (U2) is the only web module that imports dictionary values (20.3,
`lib/i18n-imports.test.ts`). Every locale is its own dynamic import, so Vite emits one chunk per locale and the
entry chunk carries none (D7):

```ts
type Loaded = { I18N_CHUNK: string; dict: PartialDictionary };
const LOADERS: Record<Locale, () => Promise<Loaded>> = {
  de: () => import('@weblion/shared/i18n/de').then((m) => ({ I18N_CHUNK: m.I18N_CHUNK, dict: m.de })),
  en: () => import('@weblion/shared/i18n/en').then((m) => ({ I18N_CHUNK: m.I18N_CHUNK, dict: m.en })),
  fr: () => import('@weblion/shared/i18n/fr').then((m) => ({ I18N_CHUNK: m.I18N_CHUNK, dict: m.fr })),
  it: () => import('@weblion/shared/i18n/it').then((m) => ({ I18N_CHUNK: m.I18N_CHUNK, dict: m.it })),
  nl: () => import('@weblion/shared/i18n/nl').then((m) => ({ I18N_CHUNK: m.I18N_CHUNK, dict: m.nl })),
};

/** The bundles of fallbackChain(locale) without 'de' (except for 'de' itself), loaded in parallel. */
export async function loadBundles(locale: Locale): Promise<Partial<Record<Locale, PartialDictionary>>>;

/** Compiled dictionary of a locale: fr = { ...en, ...fr }; de and en alone. Cached per locale. */
export async function loadDictionary(locale: Locale): Promise<Dictionary>;
```

- fr, it and nl load the en chunk too (the fallback, 2.2) and merge `{ ...en, ...fr }`; German is never loaded
  for them: en is complete by type. de and en load only themselves.
- Each loader checks `I18N_CHUNK === 'wl-i18n-chunk:<locale>'` (the reference keeps the marker export in the
  chunk for the build check, 5.4) and retries a failed import once after 500 ms. A second failure rejects.
- After a deploy an old tab may ask for a chunk that no longer exists. `main.tsx` listens to Vite's
  `vite:preloadError` and reloads the page once (flag in `sessionStorage`), the usual Vite advice.
- Results are cached in a module-level `Map`, so switching back and forth loads nothing twice.

Chunk sizes (review finding 19): a locale chunk is about 70 KB gzipped today; the build check enforces at most
90 KB per locale chunk (5.4). A French user downloads the en and fr chunks, so roughly twice that once, then from
the HTTP cache (hashed file names, `maxAge: '1h'` from `@fastify/static` in `apps/api/src/app.ts`, immutable in
practice).

### 5.3 Overrides: fetch, cache, merge, applyOverride

The browser merges database overrides (D8, 13) over the compiled bundles, so an edit in the admin shows without a
deploy.

```ts
/** Overrides of every locale in fallbackChain(locale) except 'de', newest from the server or the cache. */
export async function loadOverrides(locale: Locale): Promise<Partial<Record<Locale, Record<string, string>>>>;
```

- For each locale of the chain without `de` (fr: `fr` and `en`; en: `en`; de: `de`), a request
  `GET /api/v1/i18n/overrides/<l>` with `cache: 'no-store'`, `credentials: 'omit'` and, when a cached copy
  exists, `If-None-Match: <etag>`. `304` keeps the cached values; `200` stores `{ etag, values }` under
  `localStorage['wl-i18n-overrides:<l>']`. Errors keep the cached values (or none).
- With a cached copy the boot does not wait: it renders with the cached values and revalidates in the background;
  when the answer differs, `applyOverrides(locale, values)` updates the provider. Without a cached copy the boot
  waits at most 1,500 ms (`AbortSignal.timeout`), then renders without overrides and applies them when they
  arrive.
- `de` overrides matter only when the UI is German: German is never a fallback in the web (5.1).

Merge order, highest first: overrides of the locale, its bundle, en overrides, the en bundle:

```ts
dict = { ...en, ...overrides.en, ...bundle[locale], ...overrides[locale] }; // fr, it, nl
dict = { ...en, ...overrides.en };                                         // en
dict = { ...de, ...overrides.de };                                         // de
```

Legal keys need no web logic: the server already puts the English (else German) text into the payload of a locale
whose legal translation is stale or missing (8.1, 13), and an override always wins in the merge.

Context of `lib/i18n.tsx` (plan 2.9; F creates it with static imports, U2 makes it lazy):

```ts
export type TFunction = (key: TranslationKey, params?: I18nParams) => string;

interface I18nContextValue {
  locale: Locale;
  /** Loads the chunk and overrides of `next` first, then switches; stores the choice in localStorage. */
  setLocale(next: Locale): Promise<void>;
  t: TFunction;
  /** After a save in the admin: one override of one locale changed (value) or was reverted (null). */
  applyOverride(locale: Locale, key: string, value: string | null): void;
  /** Replaces all overrides of a locale (background revalidation). */
  applyOverrides(locale: Locale, values: Record<string, string>): void;
}

export function I18nProvider(props: { boot: I18nBoot; children: ReactNode }): JSX.Element;
export function useI18n(): I18nContextValue;
export function useT(): TFunction;
/** Switch with a toast on failure; pickers use it (6). */
export function useChangeLocale(): (next: Locale) => Promise<boolean>;
```

- `t(key, params)` = `interpolate(dict[key] ?? key, params)`; `dict` is rebuilt (memoized) when the locale or an
  override of a locale in its chain changes.
- `applyOverride` updates the in-memory map and the cached copy (and drops the cached ETag so the next load asks
  the server again). The translation admin calls it after every save, revert, import and job (17.2), so the
  editor sees the change at once; other browsers see it on their next load (the ETag changes, 13).
- `setLocale` keeps the old dictionary on screen until the new one is loaded (no spinner, no flash); on failure it
  rejects and the locale stays.

Test helper `apps/web/src/test/i18n.tsx` (F creates, U2 keeps the signature):


### 5.4 The chunk check script

`apps/web/scripts/check-i18n-chunks.mjs` (U2), run as `pnpm --filter @weblion/web check:chunks` after
`pnpm build` (script in `apps/web/package.json`; CI step after the build, plan 8.3). Plain Node, no dependencies
(`node:fs`, `node:zlib`, `node:path`). It needs no Vite manifest, so `vite.config.ts` stays unchanged:

1. Reads `apps/web/dist/index.html`, takes the entry script (`<script type="module" src="/assets/index-*.js">`)
   and the `modulepreload` links: together the "entry set" that every page loads.
2. Reads every `dist/assets/*.js`.
3. Entry markers: no file of the entry set contains `wl-i18n-chunk:` (no dictionary in the entry).
4. Each of the five markers `wl-i18n-chunk:de` ... `wl-i18n-chunk:nl` appears in exactly one file, and no file
   contains two markers (fr does not swallow en).
5. Each locale chunk is at most 90 KB gzipped (`zlib.gzipSync(buf, { level: 9 }).length <= 90 * 1024`).
6. No web chunk contains server-only texts: no match of `/["'](?:email|pdf)\.[A-Za-z0-9]+\.[A-Za-z0-9.]+["']/`
   (minified dictionaries keep their keys as quoted property names; today no key starts with `email.` or `pdf.`,
   and the shared `SERVER_ONLY_SECTIONS` keep it that way).
7. Prints a table (file, marker, raw size, gzip size) and exits 1 with one line per problem.

The check is the build-time side of 20.3. The import rule (`lib/i18n-imports.test.ts`) is the source-time side.

## 7. Error texts in the web

`apps/web/src/lib/api-errors.ts` (F creates a stub returning `errorMessage(err)`; U2 implements, O25):

```ts
/** Text for an error in the UI language: translated for known codes, the API's English message otherwise. */
export function localizeError(err: unknown, t: TFunction): string;
```

Used by every place that shows an error today through `errorMessage` (`apps/web/src/lib/api.ts:70-79`):
`useApiMutation` toasts (`lib/queries.ts:418`), `ErrorState` (`components/ui/primitives.tsx:212`), and U4's
`aiErrorText(t, err)`, which only calls `localizeError(err, t)`. `errorMessage` stays for logs and tests.

Rules, in this order:

1. Network failure (`TypeError` from `fetch`, no response): `error.network`.
2. `ApiError` with an AI code (`ai_*`, the table of ai 4.2): the first existing key of
   `ai.error.<camelCode>.<detail>` and `ai.error.<camelCode>`, where `<camelCode>` is the code without `ai_` in
   camel case (`ai_org_disabled` -> `orgDisabled`) and `<detail>` is `details.limit` for `ai_limit`
   (`ai.error.limit.budget`, `ai.error.limit.org_daily`, ...). Parameters from `details`
   (`retryAfterSeconds` as `{seconds}`, `resetsAt` formatted as `{date}`).
3. `ApiError` with an i18n code (11.4): `admin.i18n.error.<code>` with parameters from `details`
   (`placeholder_mismatch`: `{missing}` and `{extra}` joined with ", ", empty as "-").
4. Generic codes, whatever the API message says: `unauthorized` -> `error.unauthorized`, `forbidden` ->
   `error.forbidden`, `not_found` -> `error.not_found`, `rate_limited` -> `error.rate_limited`, `internal_error` ->
   `error.internal_error`; status 502, 503 or 504 without a JSON body (`code === 'error'`, a proxy page) ->
   `error.unavailable`.
5. Everything else (`bad_request`, `conflict`, `unsupported`, `provider_error`, module codes such as
   `monitor_limit`): `errorMessage(err)`, the English API message, as today.

Why the generic codes ignore the message: the default messages ("You are not allowed to do this", "Server not
found") say nothing the translated text does not say, and the specific ones are rare. Why rule 5 keeps English:
API messages are the public API contract and stay English (plan decision 7); translating every one of several
hundred messages is a later project (plan 9, roadmap "message catalog for API error codes").

Key lookup with existence check: the function builds key strings at runtime, so it checks
`key in dictionary` (a small `hasKey()` exported by `lib/i18n.tsx`) and falls through to the next rule when a key
is missing. A code added later without a key degrades to its English message instead of showing a raw key.

Tests: `lib/api-errors.test.ts` (U2): each rule, every code of plan 2.10 has a key in de and en (the test iterates
the frozen list), a missing detail key falls back to the plain key.

## 8. Server-side texts

### 8.1 The API translator and the overrides payload

`apps/api/src/i18n/service.ts` (F16, U1 keeps the signatures of plan 2.5):

```ts
export type Tr = (key: ServerTranslationKey, params?: I18nParams) => string;

export class I18nService {
  constructor(db: Database, env: Env, log: FastifyBaseLogger, catalog?: I18nCatalog /* default loadCatalog() */);
  readonly catalog: I18nCatalog;
  /** Reads every override into memory. Called once in buildApp before the routes (F17). */
  load(): Promise<void>;
  /** Refresh timer: every 15 s `select count(*), max(updated_at)`, full reload when it changed. */
  start(): void;
  stop(): void;
  /** After a local write (admin save, import, job batch, cleanup): reload now. */
  reload(): Promise<void>;
  /** Text of a key in a locale, with overrides, fallback and the legal rule. Never throws. */
  t(locale: Locale, key: ServerTranslationKey, params?: I18nParams): string;
  translator(locale: Locale): Tr;
  /** Effective German text (German override, else compiled) and its hash, for stale checks. */
  source(key: ServerTranslationKey): { text: string; hash: string };
  /** Body and ETag of A1 (13), cached until the next reload. */
  payload(locale: Locale): { etag: string; body: I18nOverridesDto };
  /** One cell for the admin (14.1): value, origin, state. */
  cell(locale: Locale, key: ServerTranslationKey): TranslationCellDto;
}
```

Lookup `t(locale, key)`: for each locale `l` of `fallbackChain(locale)`, the first of the servable override of
`(key, l)` and the compiled value `catalog.bundles[l][key]`; then the key itself. Then `interpolate()`.

A row is **servable** when all hold:

1. the key exists in the catalog (orphan rows, left from a key that was removed in a deploy, are never served
   and appear in cleanup A8, 14.2);
2. `demo = false`, or `ENABLE_DEMO_PROVIDER` is true (O11; demo rows exist only from demo jobs, 12.10);
3. for a key of `LEGAL_KEYS`: the row is current, its `source_hash` equals `source(key).hash`.

**Legal keys** (`LEGAL_KEYS` in `packages/shared/src/translations.ts`, today `ai.notice.title` and
`ai.notice.text`, O28) are never machine-translated (12.2) and never served stale (D15). For a legal key the lookup
takes, in the chain of the locale, only values that are current: an override whose `source_hash` matches, or a
compiled value whose stamp's `sourceHash` matches. If the locale has no current value, the next locale of its chain
is tried: fr -> en -> de. The effective German text is current by definition. Consequences:

- After the owner edits the German notice in the admin, every translation of it is stale and the console shows
  the German text in every language until English is updated, then English in fr, it, nl until they are updated.
- An outdated French notice is never visible, neither in the web (the payload of `fr` carries the English text for
  the key, 13) nor in a mail.

Overrides of `de`: German cells are editable like the others (the owner checks the data notice against Anthropic's
terms, plan decision 25). A German override changes the effective source: every translation of the key becomes
stale (4.1). Its own `source_hash` is the hash of the compiled German at save time, so a later deploy that changes
the German text in the repository marks the German override stale too ("the code changed since this edit").

The payload of A1 (13) for locale `L` is the servable overrides of `L` for web keys (not `email.*`, `pdf.*`),
plus, for each legal key, the text the lookup above returns when it differs from the compiled value of `L`.

Wiring (F17): `app.ts` creates the service first, `await i18n.load()`, `await seedGlossary(db)`, then
`MailService` with `i18n` as a new constructor argument. `context.ts` gains `i18n: I18nService`. `index.ts` calls
`ctx.i18n.start()`; `shutdown` calls `ctx.i18n.stop()`. Several API instances see each other's edits within 15 s;
the instance that wrote reloads at once. The cost: about 5 MB of memory at most (every cell overridden), usually
a few KB.

### 10.2 The SQL and the hand edit

`drizzle-kit generate` emits the `CREATE TABLE`, `ADD COLUMN` and `ADD CONSTRAINT` statements. F moves one

```sql
-- Hand edit: normalize stored languages before the constraint below can reject them.
UPDATE "users" SET "locale" = CASE
  WHEN lower("locale") LIKE 'en%' THEN 'en'
  WHEN lower("locale") LIKE 'fr%' THEN 'fr'
  WHEN lower("locale") LIKE 'it%' THEN 'it'
  WHEN lower("locale") LIKE 'nl%' THEN 'nl'

ALTER TABLE "users" ADD CONSTRAINT "users_locale_check" CHECK ("users"."locale" in ('de', 'en', 'fr', 'it', 'nl'));--> statement-breakpoint
ALTER TABLE "billing_profiles" ADD CONSTRAINT "billing_profiles_locale_check" CHECK (...);--> statement-breakpoint
ALTER TABLE "invoices" ADD CONSTRAINT "invoices_locale_check" CHECK (...);--> statement-breakpoint

```

## 12. Mass Translate

Translate many keys into one or more target languages with Claude, as a background job, at a cost the admin saw
and confirmed (D13). One path for every Claude call: `ctx.ai.structured()` (O4, plan 2.4). The i18n translator
`apps/api/src/i18n/translator.ts` owns batching, prompt, validation, repair and retries; `apps/api/src/i18n/jobs.ts`
owns the runner.

### 12.1 Flow

1. The admin opens "Mit KI übersetzen" (`admin.i18n.ai.button`) on the overview, the entries tab (taking the current
   filters) or a failed job ("Fehlgeschlagene erneut versuchen").
2. The dialog (`translations-dialogs.tsx`, U1) shows the availability from `TranslationSummaryDto.ai`: without a key
   or with the master switch off the note `admin.i18n.ai.notConfigured` and the link "KI einrichten" (`/admin/ai`);
   with reason `feature_off` the note `admin.i18n.ai.featureOff`; in demo mode the "Demo" badge (`ai.demoBadge`) and
   `admin.i18n.ai.demoNote`.
3. The admin picks languages (fr, it, nl preselected; en possible), the scope (untranslated, outdated, both, or all
   texts of the current selection) and the flag "Auch manuell geänderte und geprüfte Übersetzungen ersetzen".
4. "Kosten schätzen" calls B2: keys, batches, tokens, cost, the remaining monthly budget, the number of legal keys
   left out and of manual or reviewed cells kept. The dialog warns with `admin.i18n.ai.budgetWarning` when
   `costMicros > budgetRemainingMicros`, shows `admin.i18n.ai.estimateLegal` when `legal > 0`, and the cost cap note.
5. "Übersetzung starten" calls B3 with the same scope and `confirmCostMicros` = the estimate shown. B3 recomputes:
   more than 25 percent higher -> 409 `estimate_changed` (the dialog shows the new estimate and asks again); budget
   already exhausted -> 429 `ai_limit` `{ limit: 'budget' }` (O22); a job queued or running -> 409 `job_running`.
   Otherwise the job row is inserted `queued` with its fixed batch plan and the estimate, audited `i18n.job_start`.
6. The runner picks it up within 5 s (12.8), runs the batches, saves each batch's results as overrides
   (origin `ai`, reviewed false, "KI, ungeprüft") and updates the counters; the jobs tab polls B5 every 2 s while a
   job is queued or running.
7. At the end: `completed` (with or without failures), `failed` (job error, 12.7) or `cancelled`. Failures list key,
   language and reason, with "In der Liste anzeigen" (entries filtered to these keys) and "Fehlgeschlagene erneut
   versuchen" (B7, after a new estimate).
8. Results are live at once for everyone (they are overrides, 8.1); the web of the starter applies them on the next
   summary refresh. Staff review them with the filter "Ungeprüft" and mark them reviewed (A6).

### 12.2 Batching

`batches(pairs)` in `translator.ts` builds the plan at B2/B3 time:

- Input: the (key, locale) pairs of the scope after the overwrite rules (12.9), in catalog order, grouped by locale
  (all fr batches, then it, then nl), so one system prompt per locale stays in the prompt cache (12.3).
- A batch holds at most **50 keys or 8,000 characters** of effective German text, whichever comes first;
  consecutive keys of one section stay together (neighbours give context). A single key longer than 8,000
  characters forms a batch of its own.
- **`LEGAL_KEYS` are always skipped** (D15, O28) and counted in `TranslationEstimateDto.legal`; an explicit key list
  of legal keys only is refused with 409 `legal_key`.
- Keys whose German text has no letter (for example `'–'`) are skipped: the compiled value or the fallback is right
  in every language. They count as `skipped` in the estimate.
- The plan is stored in `translation_jobs.batches` as `{ locale, keys }[]` (`TranslationBatchPlan`) and never
  changes, so a resumed job (12.8) runs exactly the batches that are left. The German text itself is read at run
  time (`ctx.i18n.source(key)`), so a German edit during the job is translated in its new form and hashed with it.

### 12.3 System prompt

`systemPrompt(locale, glossary, style)` in `translator.ts`. English, fixed per locale for the whole job, sent as the
system block with `cache_control` by `structured()` (ai 6.2), so every batch after the first reads it from the
cache. It starts with the line `# Feature: translations` (O4: the demo emulator routes on it, 12.10). Outline:

```
# Feature: translations

You translate user interface texts of weblion.one, a web console of a Swiss IT and hosting business
(servers, domains, DNS, websites, e-mail, cloud storage, telephony, streaming, monitoring, invoices).
The source language is German (Switzerland). Translate into {English name} ({locale}, for readers in
{Switzerland | the Netherlands | the United Kingdom}).

Rules
1. Translate every item completely and literally in meaning. Do not add, drop or explain anything.
2. Address the reader formally: {vous | Lei, with lowercase clitics | u and uw | neutral you}.
3. Keep every placeholder in curly braces exactly as written, the same number of times. Never translate
   the name inside the braces. Keep every line break (\n).
4. Keep product, provider and protocol names unchanged (list below). Keep technical identifiers, file
   names, paths, record types, code and anything in quotes that looks like code.
5. Use the fixed translations of the glossary below whenever the German term appears.
6. Buttons and labels: short, at most about one third longer than the German. Sentence case.
7. Use straight double quotes ("). Never use the em dash (U+2014); use a comma, a colon or parentheses.
   Never use the sharp s.
8. {French only: put a no-break space (U+00A0) before ":" and "%", and no space before "?", "!" and ";",
   as in Swiss French.}
9. Do not add URLs, e-mail addresses or numbers that are not in the German text.
10. The English reference, when given, shows the meaning; translate from the German.
11. The current translation, when given, is outdated or under review: keep its wording where it is still
    right, so the console stays consistent.
12. Answer only with the JSON object of the output schema, one entry per item id.

Glossary (never translate): Anthropic, Claude, ..., weblion.one, 24fire, Proxmox, ...
Glossary (fixed translations for {locale}): Rechnung = facture; Guthaben = crédit; KI = IA; ...
Style notes for {locale}: {DEFAULT_STYLE_NOTES[locale]} {admin style notes, A14}
```

- The glossary block comes from the `translation_glossary` table (seeded with `DEFAULT_GLOSSARY`, 19.3, and the
  additions of plan 7.3): `keep` terms, then fixed translations for the locale, alphabetical.
- Style notes: `DEFAULT_STYLE_NOTES` (in `translator.ts`; the formal address rule and the Swiss specifics of
  19.2 for that language) followed by the admin's notes for the locale (settings key `i18n_style`, at most 2,000
  characters each). Admin notes are data inside the prompt: they can change tone, not the output format, and the
  validator (12.5) applies regardless.
- The prompt text contains no em dash (the review grep of plan 8.3 covers `apps/api/src/i18n`) and no model id.

### 12.4 User message and output schema

`userMessage(batch)` returns one JSON document as the user turn (the conversation ends with it, ai 6.2):

```json
{
  "locale": "fr",
  "items": [
    {
      "id": "i1",
      "key": "billing.invoice.finalize",
      "de": "Rechnung abschliessen",
      "en": "Finalize invoice",
      "current": null,
      "placeholders": [],
      "maxLength": 36
    }
  ]
}
```

- `id`: `i1`, `i2`, ... per batch; the answer is matched by id, never by key (a model may rewrite a key).
- `key`: context only (the first segment names the area, the last the role: `title`, `button`, `hint`).
- `de`: the effective German text; `en`: the effective English text when the target is not English; `current`: the
  current value of the target cell when it exists (outdated or AI unreviewed under `replaceManual`), else null.
- `placeholders`: `placeholdersOf(de)`, so the model sees what must stay.
- `maxLength`: the length limit of check 5 (19.4) for this text.

The demo emulator relies on `locale`, `items[].id` and `items[].de` (12.10); these field names are a contract with
`apps/api/src/modules/ai/demo.ts` (`emulateMessages`, plan F15).

Output schema (zod in `translator.ts`, passed to `structured()`, which turns it into a strict JSON schema with
`toStrictJsonSchema`, ai 6.5):

```ts
export const TranslationBatchOutput = z.object({
  items: z.array(z.object({ id: z.string(), text: z.string() })),
});
```

Strict structured output guarantees the shape; content is checked by the validator (12.5).

### 12.5 validateItem, steps 1 to 9

`validateItem(input: { key, locale, source, english, text, demo, glossary }): { ok: true; value: string; fixed: boolean } | { ok: false; reason: TranslationFailureReason; detail: string }`
in `translator.ts`. The same predicates as the repository checks (19.4), from `packages/shared/src/i18n/checks.ts`,
with `allowlistFor(locale)` (review finding 15):

1. **Present**: the batch answer has an entry with this id and a string `text`; else reason `missing`. Empty after
   trimming: `empty`. Extra ids in the answer are ignored.
2. **Normalize**: `\r\n` to `\n`, Unicode NFC, outer whitespace trimmed unless the German text has it.
3. **French typography fix** (fr only): `fixFrenchTypography()` turns an ASCII space before `:` and `%` into a no-break
   space (U+00A0) and removes any space (ASCII, U+00A0, U+202F) before `?`, `!` and `;`; it never touches text inside
   placeholders or `://`. `fixed = true` when it changed something. Afterwards check 11 must pass.
4. **Placeholders exactly as German**: `comparePlaceholders(source, value)` returns no `missing` and no `extra`; the
   number of line breaks is equal (`lineBreakCount`). Else `placeholders` with the lists in `detail`.
5. **Forbidden characters**: no sharp s (check 7), no em dash (check 8). Else `characters`.
6. **No new content**: every URL (`https?://\S+`), e-mail address and number (a digit run, also inside words such as
   "24fire" or "IPv6") in the value must also appear in the German or the English reference. Else `content`
   (review finding 15: an injected or invented link, address or price must never go live).
7. **Language checks** with the allowlist, skipped for demo jobs (12.10): leftover German (check 3) -> `german`,
   informal address (check 4) -> `formality`, length (check 5) -> `length`, glossary terms (check 6) -> `glossary`.
8. **French typography** (check 11, fr only) after the fix of step 3 -> `characters` (only reachable when the fix
   cannot apply, for example a space before `:` inside an allowlisted construct).
9. **Result**: `{ ok: true, value, fixed }`, or the first failing reason with a short English detail
   ("missing {name}", "new URL https://...").

The order puts cheap structural checks first, so the repair message (12.7) names the most important problem.

### 12.6 Estimate, budget, cost cap

`estimate(pairs, locales)` in `translator.ts` returns `TranslationEstimateDto` (14.1) without calling the model
(B2 needs no AI call, O9):

- Per batch: input tokens = system prompt (counted once per locale at full price as a cache write, then as cache
  reads, `AI_PRICES` of ai 2.2) + user message (JSON length / 3.2); output tokens = sum over items of German length
  x language factor (en 1.0, fr 1.2, it 1.15, nl 1.1) / 3.5 + 12 per item for JSON + 30 percent allowance for
  adaptive thinking at effort `medium`.
- `costMicros = sum of aiCostMicros(model, usage, AI_DEFAULT_MODEL)` (O7) per batch, with the model of the KI page.
- Rough size: the whole app (about 4,450 keys, 190,000 German characters) into fr, it and nl with Claude Opus 5.5
  (USD 4 / 20 per million tokens) comes to roughly USD 10 to 20, mostly output.
- `budgetRemainingMicros` from `ctx.ai.budgetState()` (ai 7.1): budget minus spent minus reserved this month; null
  when the budget is unlimited. The dialog warns when the estimate exceeds it (plan decision 12).
- Demo jobs estimate 0 (`demo: true`).

Two caps protect against a runaway job (O29, review finding 7):

- **Start refused when the cost rose**: B3 and B7 recompute the estimate for the same scope; more than
  `1.25 x confirmCostMicros` answers 409 `estimate_changed` with the new value (plan decision 10).
- **Stop at 1.5 x estimate**: before each batch and after each commit the runner compares
  `translation_jobs.cost_micros` with `1.5 x estimate_micros`; above it, the job ends `failed` with error `cost_cap`.
  Batches in flight at that moment may still commit (at most `I18N_AI_CONCURRENCY` batches).
- The **monthly budget** is enforced by the AI reservation on every call (ai 7.1); a refusal with `ai_limit`
  `{ limit: 'budget' }` ends the job `failed` with `ai_budget_job` (12.7). Completed batches stay saved.

### 12.7 Repair batches and retries

**Repair**: after validating a batch, the items that failed with `placeholders`, `characters`, `content`, `german`,
`formality`, `length` or `glossary` get one repair round: one more call for those items only, whose user message adds
per item `"previous": "<the rejected text>"` and `"problem": "<detail>"`, and whose system prompt is the same (cache
hit). Each item is repaired at most once; what fails again becomes a `TranslationFailure`. Repair calls count in the
job's tokens and cost like any other.

**Transport and model errors** of a call (ai 4.2 codes as `structured()` throws them, mapped per plan 2.6, O6):

| Error | Job does |
|---|---|
| `ai_busy` (`overloaded`, `rate_limit`) | wait (injected `sleep`) 5 s, 15 s, 45 s, 2 min, 5 min; then the batch's items fail with `error` and the job goes on |
| `ai_limit` `concurrent` | wait 5 s and retry, not counted as an attempt (other AI work has the slots) |
| `ai_limit` `budget` | stop: job `failed`, error `ai_budget_job` |
| `ai_timeout`, `ai_upstream` `server` or `network` | retry twice after 5 s and 30 s, then split the batch in two halves once; still failing: items fail with `error` |
| `ai_upstream` `output` (answer not valid JSON for the schema) | split once, then items fail with `error` |
| `ai_incomplete` (cut at `max_tokens`, the batch passes `retryOnMaxTokens: false`, O4) | split the batch in halves, recursively down to one item; a single item fails with `error` |
| `ai_refusal` | split in halves to isolate the item; a single refused item fails with `refusal` (the others are saved) |
| `ai_upstream` `auth`, `permission`, `billing`, `not_found` | stop: job `failed`, error `ai_upstream` with the reason |
| `ai_upstream` `request` | items of the batch fail with `error` (a malformed request is a bug, logged with the request id) |
| availability changed (master switch, feature off, key deleted) | stop: job `failed`, error `ai_not_configured` |
| three batches in a row failing completely | stop: job `failed`, error `ai_failed` |

Splitting keeps the plan intact: the sub-batches belong to the same plan index, which is marked done when all of its
parts are committed.

### 12.8 The job runner

`TranslationJobRunner` in `apps/api/src/i18n/jobs.ts` (U1; F creates it with the signature, plan 2.5):

```ts
export interface JobRunnerOptions {
  /** Injected for tests; default setTimeout-based sleep honouring the abort signal. */
  sleep?: (ms: number, signal?: AbortSignal) => Promise<void>;
  now?: () => Date;
  tickMs?: number;        // 5,000
  heartbeatMs?: number;   // 30,000
  staleAfterMs?: number;  // 120,000
  concurrency?: number;   // env I18N_AI_CONCURRENCY (1..4, default 2)
}
export class TranslationJobRunner {
  constructor(ctx: AppContext, pool: pg.Pool, options?: JobRunnerOptions);
  start(): void;            // tick every tickMs (unref'd timers), like BillingJob.start()
  stop(): Promise<void>;    // abort in-flight calls, re-queue the owned job, clear timers
  /** One tick, exported for tests: claim and run (or resume) a job if allowed. */
  tick(): Promise<void>;
  /** For B6: ask the owner to cancel; the runner reacts within one heartbeat or at the next commit. */
  requestCancel(jobId: string): Promise<'cancelled' | 'requested' | 'finished'>;
}
```

Wiring (F17): `context.ts` gains `i18nJobs: TranslationJobRunner`; `index.ts` calls `ctx.i18nJobs.start()` when
`I18N_JOB_ENABLED` (default true; set false on secondary processes, plan 9 deployment), and `await
ctx.i18nJobs.stop()` in `shutdown` before `app.close()`.

Tick (every 5 s):

1. On a dedicated pool client, `pg_try_advisory_lock(742_004)` (the pattern of `jobs/sync.ts:812-828`); not
   acquired: return. The lock only serializes claiming; it is released at the end of the tick.
2. If this runner already owns a running job: return.
3. Claim, in one statement:
   `update translation_jobs set status = 'running', runner = $me, heartbeat_at = now(), started_at = coalesce(started_at, now())
    where id = (select id from translation_jobs where status = 'queued' or (status = 'running' and heartbeat_at < now() - interval '2 minutes')
    order by created_at limit 1) returning *`.
   This takes over a job whose runner died (crash, kill, a deploy without a clean stop) after 2 minutes without a
   heartbeat (review finding 13). A running job with a fresh heartbeat is left alone, so two instances never run the
   same job.
4. Unlock, then run the job outside the lock (asynchronously; the tick returns).

Run:

- Pending batches = plan indexes not in `done_batches`; up to `concurrency` batches in flight.
- Each batch: read the effective German, English and current values; skip pairs that the overwrite rules now exclude
  (12.9, counted `skipped`); call `translateBatch()` (12.5 to 12.7) with the job's `AbortController.signal`; then
  commit in one transaction:
  - upsert the overrides (12.9 conflict rule);
  - `update translation_jobs set done_batches = array_append(done_batches, $i), done = done + $n, failed = failed + $f,
    skipped = skipped + $s, input_tokens = input_tokens + ..., cost_micros = cost_micros + ..., failures = ...,
    heartbeat_at = now() where id = $id and runner = $me and status = 'running' and not cancel_requested`;
  - zero rows updated (ownership lost after a takeover, or cancel requested): roll back, so the batch's overrides are
    not written, and stop working on the job.
- After each commit: `ctx.i18n.reload()` (the new values are live) and the cost cap check (12.6).
- Heartbeat: a 30 s timer (`setInterval`, unref'd) updates `heartbeat_at` where `runner = $me` and reads
  `cancel_requested`; a heartbeat even while a long call is in flight keeps the job from being taken over. When the
  update matches no row or cancel is requested, it aborts the in-flight calls.
- End: `status = 'completed'` (also with failures), `'failed'` with `error`, or `'cancelled'`; `finished_at`,
  `runner = null`; audit `i18n.job_finish` (11.2).

Cancel (B6): a queued job becomes `cancelled` at once; a running job gets `cancel_requested = true` and the runner
aborts within one heartbeat (or at the next commit); the batch in flight is discarded, committed batches stay. A
finished job answers 409 `job_finished`.

`stop()` (graceful shutdown): aborts the in-flight calls (their batches are not committed), sets the owned job back
to `queued` with `runner = null` (`where runner = $me`), clears the timers. The next start, on this or another
instance, resumes it from `done_batches` (plan 8.4 scenario 3: "restart the API while a gated job runs -> the job is
queued and resumes after the restart").

Instance id: `${hostname}:${pid}:${random}` at construction, so a restarted process never mistakes the old row for
its own.

Injected `sleep` and `now` make the retry waits and the 2-minute takeover testable without real time (20.2 cases i
and m).

### 12.9 Overwrite rules

Which cells a job may write (checked when the plan is built and again when a batch is committed, so a person who
edits a cell during the job wins):

| Current state of the cell | Job writes it |
|---|---|
| missing (no override, no compiled value) | yes |
| compiled, stale | yes (scope "outdated" or "both"); the compiled text stays in the repository, the AI text is an override |
| compiled, current | only in scope "all of the selection" |
| override `ai`, not reviewed | yes |
| override `ai`, reviewed | only with `replaceManual` |
| override `manual` (reviewed or not) | only with `replaceManual` |
| any demo override (`demo = true`) in a real job | yes (demo rows are pseudo translations) |
| legal key | never (12.2) |

The upsert is guarded in SQL: `on conflict (key, locale) do update set ... where translation_overrides.demo or
(translation_overrides.origin = 'ai' and not translation_overrides.reviewed) or $replaceManual`. A row kept this way
counts as `skipped`.

AI results are stored as `origin = 'ai'`, `reviewed = false` ("KI, ungeprüft", plan decision 11), `source_hash` =
hash of the German text the batch translated, `updated_by` = the starter, `demo` = the job's `demo`. They are live at
once; staff review them with the filter "Ungeprüft" (15) and mark them reviewed (A6) or edit them (then `manual`).

### 12.10 Demo mode

Demo mode exists only with `ENABLE_DEMO_PROVIDER=true` and no API key (O11; `availability('translations').demo`,
ai 14). It shows the whole flow without Claude:

- B2 estimates 0; B3 starts a job with `demo = true`; the dialog shows `admin.i18n.ai.demoNote` and the job the "Demo"
  badge.
- Every call still goes through `ctx.ai.structured()` and the real SDK, against the in-process emulator
  (`demoFetch`, ai 14). The emulator recognizes the feature by the first system line `# Feature: translations`
  (12.3), parses the user message (12.4) and answers `{ items: [{ id, text: "[FR] " + de }] }` with the locale code in
  capitals. The German text keeps placeholders, line breaks and glossary terms intact, so the structural checks of
  12.5 pass; the language checks (step 7) are skipped for demo jobs.
- Results are saved like real ones (origin `ai`, unreviewed) with `translation_overrides.demo = true`, cost 0, one
  `ai_usage` row per batch with `demo = true`.
- Served only while `ENABLE_DEMO_PROVIDER` is true (8.1 rule 2); deleted in the transaction of `PUT /admin/ai/key`
  (`deleteDemoOverrides(tx)` in `apps/api/src/i18n/entries.ts`, ai 5.4) and by cleanup A8 with `demo: true`.
  The admin shows their number (`TranslationSummaryDto.demoOverrides`) with `admin.i18n.cleanup.demoNotice`.
- A real job overwrites demo rows (12.9).

## 13. The public endpoint A1

`GET /api/v1/i18n/overrides/:locale` in `apps/api/src/modules/i18n/routes.ts` (F16 implements it).

- **No auth**: the login page needs its overrides before anyone is signed in. The texts are UI texts that the
  public JS bundle carries anyway; nothing private is in them. Rate limit 120 per minute per address (11.3).
- `:locale` must be one of the five; anything else is 404 `not_found` (the existing not-found body).
- Body (`I18nOverridesDto`, 14.1): `{ locale, values: Record<string, string> }` = `ctx.i18n.payload(locale).body`:
  servable overrides of web keys (8.1: orphans never, demo rows only with `ENABLE_DEMO_PROVIDER`, `email.*` and
  `pdf.*` never) plus the legal substitutions (a legal key whose translation in this locale is stale or missing
  carries the English, else German, text).
- **ETag**: `"<16 hex of SHA-256 of the canonical JSON body>"`, cached per locale in the service until the next
  reload. Headers `ETag` and `Cache-Control: no-cache` (the browser revalidates every time; the web sends
  `If-None-Match` itself, 5.3).
- **304** without a body when `If-None-Match` equals the current ETag (also the weak form `W/"..."`, and a list of
  tags).
- Deterministic: keys sorted, so the same rows always give the same ETag across instances.
- A deploy that removes a key makes its rows orphans: they leave the payload (the ETag changes) and wait for cleanup.
